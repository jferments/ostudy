# ostudy

**ostudy** is a free, local-first desktop flashcard application. It runs without an account or application server and keeps decks, cards, documents, images, review history, settings, search indexes, and analytics on the user's computer.

## What it can do

- Create, rename, archive, and delete decks.
- Create and edit rich-text flashcards with managed local images.
- Upload a PDF into a managed document library and automatically create a flashcard deck from locally extracted structure/text and rendered pages using the configured AI provider profile.
- Process large PDFs as many small semantic AI requests instead of one large prompt; outline fragments are assembled natively and later generation uses only relevant outline sections.
- Render PDF pages through a bounded multicore pure-Rust worker pool while preserving ordered durable page persistence.
- Keep failed PDF generations available for retry with source-window-aware diagnostic errors, and open the managed source PDF in the operating system's default reader.
- Add reusable tags and filter cards by one or more tags.
- Search questions, answers, and tags with the local SQLite FTS5 index.
- Browse cards across the whole library with schedule filters, sorting, multi-selection, and keyboard navigation.
- Add many plain-text cards in one transaction with bulk entry.
- Detect exact normalized duplicates and skip or explicitly allow them.
- Move cards between decks while preserving review history, or copy them with fresh schedules.
- Import and export complete `.studydeck` deck files, and directly import strict content-only `.ostudy.json` files generated by an LLM or other authoring tool.
- Export and restore a complete `.ostudybackup` containing the SQLite library, managed card images, and managed PDF files while excluding AI credentials.
- Practice one or more decks with spaced-repetition scheduling.
- Rate each revealed answer once on a four-level confidence scale: **0 Wrong**, **1 Hard**, **2 Medium**, or **3 Easy**.
- Review confidence, response-time, due-card, and per-deck analytics.
- Configure themes, typography, scale, motion, review preferences, and local/LAN/cloud AI provider profiles.

PDF extraction and page rendering occur locally in the native application. Provider traffic also originates only in Rust. ostudy does not install a model server and never silently falls back from a configured local provider to a cloud provider.

## Ubuntu setup

From the repository root, run the setup once:

```bash
./scripts/setup-ubuntu.sh
```

The setup script installs the required Ubuntu packages and pinned development tools, installs dependencies from the committed lockfiles, and creates the first standalone debug build. Cargo uses all detected CPU cores by default. To limit parallel compilation, set `CARGO_BUILD_JOBS`, for example:

```bash
CARGO_BUILD_JOBS=16 ./scripts/setup-ubuntu.sh
```

## Start the application

Launch the already-built application:

```bash
./run-app.sh
```

This does not start a development server or rebuild the project. After changing source code, rebuild first:

```bash
./scripts/build.sh
./run-app.sh
```

Build and development commands treat `src-tauri/Cargo.lock` as immutable. If the lockfile no longer matches the Rust manifests, the command fails instead of silently rewriting it.

## Test a change

Use the tier that matches the current stage of development:

```bash
./scripts/check-changed.sh
./scripts/check-static.sh
./scripts/check-fast.sh
./scripts/check.sh
```

The static tier verifies environment, migration, dependency, IPC, repository, type, formatting, and test-policy contracts. Fast adds the complete frontend suite and locked Rust compile checking. The full gate adds production/native builds, Clippy, all Rust/database/migration tests, dependency verification, and real Tauri/WebDriver persistence smoke tests. After the full gate passes, start the app with `./run-app.sh` and manually exercise the changed workflow. See `docs/development/testing-and-ci.md` for details.

## Local data and deck sharing

The Settings screen displays the active database and managed-image locations. The Documents screen manages immutable source PDFs and direct PDF-to-deck generation. Full-library backups preserve both card images and managed documents.

Deck sharing uses `.studydeck` files, which are versioned SQLite packages that contain deck content, tags, and managed card images. They intentionally exclude personal review history, application settings, AI credentials, and managed source PDFs.

Cards are stored as validated structured documents rather than executable HTML. Shared decks and model output cannot supply executable content, database operations, arbitrary local file paths, or remote images for the application to execute or load. Search input is converted into quoted FTS5 tokens and all SQLite values are bound parameters.
