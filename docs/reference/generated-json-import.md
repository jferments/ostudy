# Generated JSON flashcard import

## Status

Version 1 defines and implements a content-only JSON format for importing flashcards generated by an LLM or another external authoring tool.

This boundary is intentionally separate from:

- `.studydeck`, which remains the portable single-deck package for sharing deck content and managed images;
- `.ostudybackup`, which is the full-library disaster-recovery package.

Generated JSON imports never carry internal IDs, schedules, review history, analytics, application settings, reusable template IDs, local paths, HTML, or image bytes.

## User workflow

The Decks screen has one **Import deck** button. Its file picker accepts either:

- `.studydeck` deck packages; or
- generated `.ostudy.json` files.

There is no generated-import preview window and no separate generated-import button. Selecting a valid file immediately runs the appropriate transactional importer. Success opens the imported destination deck. A validation or destination error is shown through the ordinary application error toast and leaves the library unchanged.

## File identity

The recommended filename suffix is `.ostudy.json`. The file itself is ordinary UTF-8 JSON with this envelope:

```json
{
  "format": "ostudy-flashcards",
  "formatVersion": 1,
  "deck": {
    "mode": "create",
    "name": "Required deck name",
    "description": "Optional description for a newly created deck"
  },
  "defaultTags": ["optional shared tag"],
  "cards": []
}
```

The importer rejects unsupported versions and unknown properties rather than silently discarding data.

## Destination behavior

The JSON file owns the destination decision.

### Create

```json
"deck": {
  "mode": "create",
  "name": "NCLEX Pharmacology",
  "description": "Medication safety and nursing priorities"
}
```

`create` always creates a new deck. Another deck may already have the same displayed name; no existing deck is replaced.

### Append

```json
"deck": {
  "mode": "append",
  "name": "NCLEX Pharmacology"
}
```

`append` requires exactly one active deck whose name matches exactly. `description` must be omitted or empty. Import fails when there is no exact match or when multiple active decks have that name.

## Card types

### Basic

```json
{
  "type": "basic",
  "front": "Restricted Markdown question",
  "back": "Restricted Markdown answer",
  "reverseEnabled": false,
  "tags": ["optional tag"]
}
```

A reverse-enabled Basic note creates independently scheduled forward and reverse presentations.

### Fill in the blank

```json
{
  "type": "cloze",
  "text": "The {{c1::sinoatrial node}} is the normal cardiac pacemaker.",
  "mode": "one_at_a_time",
  "tags": ["optional tag"]
}
```

The mode is `one_at_a_time` or `all_together`. Cloze source uses the existing bounded `{{cN::text}}` grammar and produces one stable scheduled card.

## Restricted Markdown

Basic sides accept:

- paragraphs and headings;
- bold, italic, strikethrough, and inline code;
- fenced code blocks;
- block quotes;
- ordered and bullet lists;
- absolute `http`, `https`, `mailto`, and `tel` links;
- hard line breaks and horizontal rules.

Raw HTML, embedded or remote images, local file paths, tables, executable content, and unknown syntax are rejected **when they occur as Markdown/source syntax**. Literal comparison characters such as `2 < 3` or `5 > 4` are ordinary text and are not treated as HTML. Syntax-looking text inside a supported inline-code span or fenced code block is literal code and is not reinterpreted as HTML, an image, or a table.

The restricted parser decides which Markdown syntax is supported; Rust then converts accepted syntax into canonical Tiptap JSON and runs the ordinary card-content validator, which remains authoritative for safe rich-document structure, links, sizes, and derived plain text.

## Validation and commit

The importer reads and validates the whole file before starting its write transaction. Semantic card errors are collected and reported with their `cards[index]` paths. If any card is invalid, nothing is written.

After validation:

1. Rust resolves the deck destination from `deck.mode` and `deck.name`.
2. Exact duplicates within the file or destination deck are skipped automatically.
3. Accepted notes, tags, generated directions, and fresh local schedules are written in one transaction.
4. Any database failure rolls back the entire import.

The file cannot request replacement, deletion, overwrite, schedule preservation, or duplicate bypass.

## Executable conformance corpus

The repository contains two reviewable test fixtures under `tests/fixtures/generated-import/`:

- `valid-conformance.ostudy.json` is a real version-1 import file containing a wide range of supported Basic, reverse, Cloze, Markdown, Unicode, tag, line-ending, code, list, quote, link, and punctuation forms.
- `conformance-corpus.json` is test metadata describing invalid envelopes and cards. The Rust harness materializes each invalid case as its own real `.ostudy.json` file so one invalid card does not prevent the valid corpus from proving successful imports.

The full Rust test suite verifies at least:

- every documented block and inline Markdown construct;
- literal `<`/`>` comparisons and syntax-looking text inside code contexts;
- Basic/reverse behavior and both Cloze modes, including repeated/out-of-order/max group IDs;
- strict unknown-field/type rejection and unsafe/unsupported links, HTML, images, tables, malformed Markdown, tags, and Cloze markers;
- the 10,000-card limit and 16 MiB file-size limit, plus tag/Cloze boundary values;
- exact-name `create`/`append` rules and ambiguous/missing destinations;
- duplicate skipping within/destination imports;
- fresh generated-card schedules and absence of review history;
- all-or-nothing behavior when a file contains both otherwise-valid and invalid cards.

The harness never touches the user's real application data. It uses a disposable test database and a unique temporary filesystem root, explicitly removes the imported deck/note/card/schedule/tag graph when the scenario finishes, and uses RAII cleanup so the temporary directory is removed even if an assertion fails.

## Durable invariants

- One input file targets one deck.
- Imports create fresh local schedules.
- All accepted writes use the same Rust authoring, tag, duplicate, cloze, generated-card, and scheduling logic as the ordinary editor.
- Validation or persistence failure leaves the library unchanged.
- Existing `.studydeck` behavior is unchanged.
- Format version 1 remains readable after release; incompatible additions require a later version.
