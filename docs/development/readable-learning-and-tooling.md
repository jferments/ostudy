## Implementation boundaries

Study-guide planning and authoring must be separate from the shared flashcard selection policy. Organize the complete retained topic catalog before authoring, retain deterministic identities/order and support selections, and invalidate only incompatible derived guide checkpoints. Previously generated guides remain readable; regenerating a guide must not rewrite learner cards or reviews. Large documents require bounded grouping/authoring, not topic omission, arbitrary first-N sampling, or a demand to split the source manually.

### Study-guide sizing, recovery and preservation

The guide owner separates three concerns. `study_guide/policy.rs` derives flexible writing targets from the supplied knowledge-unit count and statement size. `completion.rs` fits visible output and recovery headroom against the actual task context. Defensive per-field, array and aggregate capacities bound one generated object and are shared by the provider schema and native admission. Page count is not a proxy for how much a topic needs to explain. Writing targets are planning estimates, not token-usage measurements, factual-coverage certificates or rejection thresholds.

Each section field has one job, stated in the section system prompt: the overview orients in a few sentences, explanations teach, and tables, steps, terms, key points, callouts, misconceptions and checks appear only when they add something the prose does not already say. The overview's writing target is about an eighth of the section, between 400 and 900 characters. At admission, `study_guide/dedupe.rs` drops whole key points, callouts and important terms whose every sentence repeats an earlier sentence of the same section (80% of its content words). It never edits prose, steps, tables or checks, so no qualification is cut; this is the only place admission removes generated items. Fixed instructions sit in the system prompt and the whole-document plan precedes the section's own topic, so the sections of one document share a cacheable request prefix.

After a section is written, `study_guide/coverage.rs` names the core knowledge units of its catalog (document-core or core importance) that the section did not select as taught. When there are any and the section has room, one follow-up request sends the written section and those units, without images, and asks for at most six short explanations of facts the section does not already teach, each placed after the explanation it follows. Additions whose every sentence restates the section are dropped, new links stay within the 64-unit section bound, and the result passes the same native checks as a fresh section. The follow-up is best effort: any failure keeps the section as written. It runs before the section is checkpointed, so a resumed guide does not repeat it.

A 4,553-character overview is not invalid merely for exceeding the former 4,000-character writing cap. Exceeding a flexible target produces bounded diagnostics, not an additional paid request. The generated object remains resource-bounded: 65,536 total human-readable Unicode characters and a separate 384 KiB candidate-envelope bound, with field capacities below the existing durable normalizer's clipping boundaries. These are defensive capacities, not desired prose lengths. Unsupported selections, malformed fields, empty required content and invalid table shapes remain failures.

The guide-specific two-attempt recovery owner preflights the actual repair prompt, including retained candidate data, before reserving credit or calling a provider. Targeted repair cannot rewrite valid sibling fields. An independently validated original may survive an optional style repair that is invalid, does not fit or has no credit left. Cancellation, changed profiles and unknown operational errors are never hidden by that fallback. Truncation recovery reduces optional output breadth without removing supplied evidence or forbidding every useful visual/mechanism explanation. Nothing silently enables reasoning or changes provider.

Document topic partitions are checkpointed as they succeed using the existing checkpoint table. Reuse requires matching plan/model contract, partition request identity, source evidence, content hash, catalog fingerprint and valid support. A later partition failure therefore need not regenerate earlier paid output. Topic assembly retains distinct overview paragraphs in deterministic order instead of substituting a planning summary. A preservation check refuses any durable normalization that would discard text or array items; an exceptional assembly-capacity error leaves successful checkpoints available instead of publishing clipped qualifications. The versioned guide checkpoint contract prevents reuse of old lossy topic assemblies. It does not invalidate shared knowledge or learner flashcards and does not delete existing published guides.

First-key defaults are an onboarding decision, not a hard-coded capability certificate. The exact public model identifiers were verified against OpenRouter's model pages on September 27, 2026. Model availability remains a runtime discovery/probe concern. Saving a key does not authorize a fallback provider or automatic library-wide embedding upload.

Tooling changes should remove incidental source-layout dependencies without making another status service or general test framework. Generated metadata is compared during qualification; Actions never write maintained source. All destructive filesystem tests use disposable data.

Generated JSON is a text-only interchange boundary. Version 2 covers every text-native scheduled card/question family: Basic, Cloze, single-choice, select-all, true/false, matching, grouping and ordering. Image occlusion is intentionally excluded because importing it safely requires a package that carries and owns managed image assets rather than JSON that references nonexistent local files.
