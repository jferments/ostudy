# UI architecture

One React presentation serves Linux and Android through capability-oriented platform adapters. [The comprehensive architecture](overview.md) covers the system; this reference owns current UI composition, interaction, state and styling. PR #96's completed migration is preserved in the [UI implementation record](../development/ui-overhaul-current-implementation.md) and [migration roadmap](../development/ui-overhaul-roadmap.md). The active post-migration aesthetic work is tracked separately in the [visual refresh roadmap](../development/ui-visual-refresh-roadmap.md).

## Responsibilities and dependency direction

```text
feature screen -> controller -> typed IPC -> native domain
       |              |
       v              +-> platform capability adapter
  oStudy UI facade -> owned shadcn source -> Base UI + Tailwind
```

Screens compose controllers, typed read models and semantic UI. Controllers own asynchronous domain reads/mutations, request identity and reconciliation. `src/ipc` owns direct native invocation; `src/platform` owns OS-facing frontend adapters. Shared `src/ui` must not import IPC, feature controllers or Tauri APIs.

This diagram is an ownership rule, not a claim that every feature is a pure view. General controllers are in `src/controllers`; focused library hooks/models are colocated with that feature. Refactor with behavior tests rather than arbitrary file-size targets.

Rust owns durable content, validation, transactions, schedules, history, processing and provider policy. Efficient UI projections do not make React's layout the data model. No screen performs SQL or contacts an AI provider directly.

## Root composition and state

`main.tsx` composes providers and imports one foundation stylesheet. `App.tsx` renders lazy feature roots inside AppFrame/AppContent. `useAppController` owns navigation, active workflows, dirty guards, Practice launch/exit and checkpoint integration. TutorProvider shares top-level/contextual Tutor state; DocumentJobsProvider keeps document jobs alive across navigation; HomeSummaryProvider holds the native home summary and the subject library for Home, Review and Review's badge.

Destination state and an active Practice workflow are separate. Contextual launch is a semantic request, not a tab selection. Consuming a one-shot payload must not unmount the session. Exit guards run before same-destination short-circuiting.

Independent reads use independent request lanes. An obsolete success/error must not replace current state. Durable mutation completion has different semantics: a committed operation remains successful when a subsequent refresh or navigation fails. Reconciliation is reported separately and supported retry identities are preserved.

## Restoration and compatibility

The schema-v2 device-local checkpoint separates destination from a real resumable-session hint and logical return target. Native SQLite owns session progress; the checkpoint is not a serialized React store or a content backup.

Supported schema-v1 data normalizes through native code. Setup-only Practice does not masquerade as a running session. Restoration uses fresh transition identities; deleted targets fall back without inventing missing content. Legacy Cards/Templates checkpoint and Flashcards-workspace values are accepted only at their compatibility boundaries and normalize to current destinations before reaching live React route state. The application sections the checkpoint stores are home, overview, lessons, podcasts, decks, study-guides, documents, notes, review, tutor, analytics and settings; the navigation presents them as the five destinations (overview is Library's own page, and lessons, podcasts, decks, documents and study-guides a subject's tabs; notes is Notes; analytics is Progress; review shows Home; settings opens from its header button). The chosen Library subject is process-local and never stored, so a restored subject page other than Flashcards opens Library's page and a restored Workbench shows All cards, and the live Flashcards route workspaces are exactly decks and search, which the Workbench reads as All cards and All cards with search focused. A checkpoint written by an older build names only the older sections and still opens; an older build that finds a section it does not know (podcasts, for one) quarantines the checkpoint and opens Home. Selection remains transient. See [ADR 0050](../decisions/0050-versioned-ui-checkpoint-workflow-restoration.md).

## Home and Library

Home is the landing page. HomeSummaryProvider reads `get_home_summary` and the subject library as independent latest-request lanes, and reads them again when Home or Review opens, when a session reaches its summary or ends, when the deck list or a document's processing state changes, when the saved daily limits or new-day hour change, and when the app becomes visible, since the study day may have turned over. Rust computes the counts with the rules a scheduled session applies (studyability, the study date, which starts at the **New day starts at** hour, and the shared daily limits), so the Today strip, Home's badge and Library's Review buttons all count what Start review studies: scheduled reviews plus scheduled new cards over the decks the summary lists. The question of the day is a second read-only command, `get_question_of_the_day`: Rust picks one studyable recall card per study date with a weighted draw seeded by the date and card id, leaning toward new cards and cards with lapses, relearning or high difficulty, so the pick holds all day and changes when the study day turns over. Turning it over records nothing.

A subject tile shows its due count, sources and cards, a status line from real state (preparing a document, all done, or whether an overview guide exists) and its remembered rate over 30 days, read once per refresh from `get_progress_subjects` in its own lane (a bar on wider screens, part of the line on phones; nothing while it loads or when it fails). Subjects store no color: the theme's six subject colors follow creation order, so moving or re-sorting subjects never repaints one, and the sort choice lasts until the app closes. No subject appears only for unfiled decks or documents, and a quiet notice opens Check these when the upgrade left items to check. A library with nothing in it gets the first-run welcome; one whose decks are all archived is titled Nothing to study yet and offers Open Library instead of being called empty. The welcome's heading has no explanatory paragraph; its Create a subject and Import a document open New study set. Below them `HomeGettingStarted` offers Import a deck (the deck import dialog, then the imported deck), Take a tour (`ProgramTour`, a Dialog with one stop per main place and AI last) and, while AI is off, the AI tip with Set up AI and Don't show this again (`ostudy.homeAiTip.v1` in local storage); a Home with subjects keeps only the AI tip, under the Today strip. A subject opens its Flashcards in Library (`openSubject(subjectId, page?)`, which chooses the subject, `null` choosing No subject, and opens the page named, the Workbench by default), and Resume on a lesson opens its subject's Lessons page with the lesson playing.

Library has one entry point, `openLibrary(scope?)`: no scope opens Library's page of subjects, `subjectId` chooses that subject and opens its cards in the Workbench (`null` is No subject) and `deckId` opens a deck. Home's Open Library (offered when every deck is archived) and a deck imported from Home's welcome use it; `openAllCards` opens the Workbench on every card.

`LibraryHome` is Library's own page. Each tile (`LibrarySubjectTile`) draws the subject's figure from the home summary's `cover` (the native side picks the most worth-studying, most important figure covering at least 3% of its page, and the page renders its crop through `render_document_page_tile`, kept for the run) or the subject's initials on its color, then its name (which opens Flashcards), what it holds or is preparing, its due count, its menu (`SubjectActions`) and a button for each kind of material: Flashcards and Documents always, Guides, Lessons and Podcasts when the summary counts any.

## Without AI

Whether AI features show is one value, `useAiFeatures().enabled` from `src/controllers/AiFeaturesProvider.tsx`. App reads it with `useAiFeaturesSource(section)` (true once an enabled AI service exists, read again whenever the section changes, so setting AI up in Settings shows the features on leaving it) and shares it with `AiFeaturesProvider`; a build made with `VITE_OSTUDY_AI=off` never shows AI features. Every AI-only surface reads it, or renders inside `AiOnly`, and nothing else changes, so cards, review, notes, documents and their marks work the same either way:

- Navigation and pages: the Tutor destination; a subject's Lessons, Study guides and Podcasts tabs; Library tiles' Guides, Lessons and Podcasts buttons and counts; Home's lesson panels; `TutorEntryButton`. While AI is off, App shows `sectionWithoutAi(section)`: Home for the Tutor and a subject's Flashcards for its AI pages, without rewriting the saved checkpoint.
- Making things: New study set becomes New subject (name and documents, no prompt or materials); Documents drops Make study materials, Images…, the PDF images question, Figures, Reading range, Leave out of study materials, Make more cards, Retry and the study guide actions and the made-materials summary; the annotator's Suggest a question; card templates' Question mix and AI labels.
- Documents are read without AI through `start_document_preparation`, which extracts, renders and chunks the document like the first step of generation and settles it ready (`record_document_prepared`) instead of failed for having no deck.

Outside a provider the value defaults to enabled, so component tests see AI features as before. A new AI-only control reads the same value; one that also needs a particular task model keeps its own missing-model check (`useGenerationModelMissing`).

## Library by subject

`LibraryFrame` hosts a subject's pages: a Library back link, the chosen subject's header (`LibrarySubjectHeader`: name, document and card counts, Practice a mix, Review N due over the subject's due decks, and the subject's own menu: Rename, Move up, Move down, Delete) and `LibraryTabs` (All cards shows the Workbench with neither). Library's page of tiles is the only list of subjects in Library; no page repeats it. Subject writes read the current revision first and hand the answer to `HomeSummaryProvider.acceptLibrary`, and the Workbench and Documents take the newest subject library either side has, so a rename, reorder, delete or move shows everywhere at once. The subject (`LibrarySubjectScope`: all, a subject, or none) lives in the app controller for the run, never in the checkpoint, and stays chosen across pages and destinations. The frame keeps one tree whether or not a page has the whole page, so the subjects, header and tabs come and go without remounting the page below them. An open study guide, a playing lesson, the document annotator or a phone's card editor takes the whole page (`useLibraryFullPage`): the subjects, header, tabs and the frame's inset step aside, so the page's top bar sticks right under the app header, and its back button returns to the page with the tabs. A page adds its own actions beside the tabs with `useLibraryTabActions`, as the Workbench does with Import deck on wider screens; a phone's tab row holds only the five tabs, and the Workbench tree offers Import deck beside New deck.

Each tab shows the chosen subject. Lessons is the subject's course (`LessonsSection`). A lesson opens as its lecture (`LessonPlayer` around `LectureView`, the whole page wide): a filmstrip of the slides against the page's edge, the slide as large as the page allows, and under it the notes or the teacher's talk, the step's own reading behind Read this step, its check with the answers two by two, and its cards; showing a step's slide saves the learner's place and Finish lesson on the last slide marks it done. There is no separate step view. When Settings › AI › Make lecture audio with new lessons is on (the default) and a lesson voice is set up, a newly written course has each lesson's narration spoken and kept straight away (`makeLectureAudio`); a step that fails is spoken when played and Podcasts its podcasts (`PodcastsSection`), while No subject has neither, since they belong to a subject. Study guides passes the subject to `list_study_guide_page`, whose filter puts a document guide in its document's subject and a subject guide (study target kind `collection`) in its own. Documents lists the subject's documents, or the unfiled ones under No subject; its search filters the loaded list by title and file name in the page, without a native query; Upload files a document into the chosen subject. Flashcards opens the Workbench on all of the subject's cards.

## Library Workbench

The Workbench (`src/screens/library/workbench/`) is Library's editing view, on its Flashcards page. The tree has no subject level: it starts with all of the chosen subject's cards (All cards for every card, Unsorted cards under No subject), then the subject's decks with New deck, its archived decks, and the tags its decks use (`list_tags` over those decks). Under All cards the decks are every live deck, each with its subject's badge. Choosing an entry sets one scope (`WorkbenchScope`: a view, a subject, a deck or a tag, a tag chosen in a subject carrying that subject so the search keeps to its decks; the tree offers only the All cards view, and older launches may still name another), and the card list shows that scope's cards through the ordinary paged card search, 100 rows at a time in a VirtualList. Decks and subjects list cards in source order (by the slide or page their notes cite), and a Show filter (All cards, Due today, New, Often missed, Suspended, each with its count) narrows any scope. The open card's editor has one sticky action bar (Preview card, Save, a card menu with Move / copy, Suspend and Reset, and × to close), shaded headers on each field, and its schedule summary below the fields. Medium and wide screens put the tree and the list side by side in ResizablePanes, and the editor opens as a panel over the list; the list stays mounted (inert) underneath, so closing the editor returns to the same scroll position, search, filter and selection. Phones show one page at a time. Pane widths are a per-device convenience in local storage.

An empty library shows one create-deck state, New deck plus Import deck, and archived-only libraries keep their decks behind Archived decks. Subjects are created from Library's page and renamed, reordered and deleted from the subject header's menu; decks move between subjects through a Move to subject sheet, and documents through the same sheet on Documents; each write carries the library revision it read, and a conflict reloads authoritative state instead of overwriting newer order. Deck actions (Practice, Practice with options, Rename, Move to subject, Move up and down, Merge into, Export, Archive and Delete with Undo) live in each deck's menu and the deck header. Merge opens a destination sheet, captures one operation identity and both deck revisions and counts, and retries an ambiguous native reply with the same request rather than issuing a second move.

Card selection is a set of card identities in the current scope. Shift extends it over a range, and Select all resolves every matching card through `list_matching_cards` rather than only the loaded rows. Move, tag, remove tags and delete work on the selection's source notes, so a forward and reverse card sharing a note count once; suspend, resume, bury, unbury, reschedule and reset work on its cards. A schedule action keeps its mutation identity until it succeeds or is rejected, so retrying after an ambiguous reply cannot apply it twice. A committed change stays committed when the following list refresh fails; the refresh trouble is reported separately.

The Workbench reads where to open from the Library route (`workbenchLaunchFor`): a deck, a subject from Home or Manage, a tag from Progress, or All cards with search focused from the header's Search. It reports the open deck back through `recordLibraryDeck`, without a new launch request, so practice returns to that deck and the checkpoint reopens it.

## Authoring and transfers

A deck's New card and Bulk add use that deck as a fixed destination; the card editor opens over the list rather than as a separate route, and leaving it with unsaved changes asks first. Search is the same card list over All cards, not a second authoring route.

Source notes and generated card presentations remain distinct. Select visible/all matching resolve different identity sets. Bulk mutations account for forward/reverse cards sharing a note. Tags use stable IDs rather than display names.

The editor adapter exposes supported commands without distributing a Tiptap instance. Durable drafts and canonical commits have separate lifecycles. Editor and template chrome use shared controls; rich content, media/math, ProseMirror descendants and print styling remain specialized. See [rich-document editor](rich-document-editor.md).

Transfer UI presents native import/export/share operations. Anki completion is a post-commit receipt; refresh/navigation failure cannot permit duplicate importing. Unknown progress remains indeterminate. Sync UI keeps sender-selected categories, Documents/Guide and settings/key dependencies, credential availability and distinct USB/LAN flows. Appearance preferences remain device-local.

## Study Guides, Documents and Tutor

StudyGuidesScreen owns bounded paginated summaries, drawn as a grid of guide cards (subject guides as stacked cards) with a search that runs as the learner types and a Sort select beside it; each card has Open and one overflow menu (Ask Tutor, Export PDF, Remake for a document's guide with its progress bar on the card, Open the source, Delete). `study-guides/exportGuidePdf` is the one PDF export the card and both readers use; `study-guides/useGuideRemake` follows guide runs through the durable artifact-job projection, so a run started on Documents shows on its card too. Opening one guide hydrates its reader and hands it what the row knows about the source file (format, file name, unit kind and count) for its file-kind badge and length. StudyGuideDialog is internally named a dialog but is the Chapter reader: an InlineWorkspace in its page presentation, with an overview page and one page per section. The outline (a nav landmark with `aria-current` on the current page and the current section opened to its headed blocks) sits beside the reading column on wide screens and opens from Contents in a Sheet on medium and compact ones. A margin rail holds the section's note, important terms, source and cards on wide screens; narrower layouts place those blocks after the section, and compact adds a sticky bottom bar with the neighbors and Practice that gives way while the section's end, with its own practice and next links, is on screen. The reading column uses the card font on the type scale. Guide-level actions sit in the top bar and its overflow menu; section-level ones in the section's menu. Notes, section rewrites and the PDF export open in the shared Sheet. Check-yourself progress is in-memory reader state, not stored. The `study-guides/` folder holds the reader's pages, outline, dialogs, the pure guide model (reading order, effective titles, reading time, locator ranges, file kinds, outline blocks) and StudyGuideStructuredContent, which the subject guide (`CollectionStudyGuideDialog`) also renders.

Generated revisions differ from learner-owned notes/overrides. Generation belongs to the retained document's action; its single active control becomes Stop. Internal revision badges and redundant regeneration controls are not ordinary reader UI. Conflicts remain visible.

DocumentsSection retains the actual unavailable-capability fallback. DocumentsScreen displays application-lifetime controller/native state; a route unmount cannot cancel durable jobs. Parsing, OCR and provider/storage policy remain native/domain-owned. The page shows no model, instructions or AI-setup panel (AI setup belongs to Settings): each document is a row with its status, Open and one overflow menu. While a document is processing or making a guide, the row instead shows one bar from `DocumentRowProgress` (`combinedArtifactProgress` averages the parts being made, and a failed part returns its full panel below the row), and its menu leads with Generation details, the Details dialog with the per-part panel and live request statistics. Learner-authored flashcard guidance is asked for when making more cards (and in the image-set workspace), but React owns only the draft: the native request captures the normalized instructions, binds them to request identity, and keeps the current run immutable. There are no collections in the interface: a subject is the record the native side still calls a document collection, and the page shows it only as its documents. `useDocumentFiling` reads the shared subject library and writes `move_document_to_subject`, `set_document_study_ranges` and `set_subject_left_out_documents` against the current document filing revision; a row's menu offers Reading range, Leave out of (or Use in) study materials, Add to or Move to another subject, and Remove from subject, and a loose row under No subject has Add to. A left-out document stays filed but is not a member of its subject's source set (`collections::load_membership_sources`), so the subject's bundle, collection view, course and Tutor scope all skip it. In a subject, `SubjectStudyActions` reads the subject's StudyTarget (kind `collection`) status and offers Make study materials beside Upload until the materials exist (a sheet chooses the documents, flashcards, the study guide and lessons, and for documents without cards the deck their first cards go into and instructions for them: the chosen documents become the subject's left-out set, documents without cards start their first cards through the jobs controller's `retry` with `destinationDeckId`, and once those runs end the flashcards and guide become the bundle's output policy and lessons start the subject's course through the application-lifetime `useSubjectCourse` run, so one Make writes both side by side and one Stop stops both), then Study and Read guide, with Update when sources change. Study starts practice over the subject, which the native side expands to the decks filed in it when the session starts; subject flashcards take no instructions because nothing is copied. Ambiguous responses retain the same durable operation identity and captured instructions; a later refresh failure is reported separately from a committed bundle. The native collection commands remain as the compatibility API under the subject library; the interface no longer calls them for filing.

The document annotator (`src/screens/documents/annotator/`) opens from a PDF's Annotate action as an InlineWorkspace page. Its pointer input runs through `AnnotatorGestures`, a pure state machine that turns pen, touch and mouse samples into effects (a draft stroke, a committed annotation, a move, an erase, a scroll, a zoom), so palm, pinch and pen-only rules are tested without a DOM. A pen outranks fingers while it is down, a second finger turns an unfinished stroke into a pinch, and only a lifted pointer commits; a stylus's eraser end erases with any tool. The canvas is the DOM adapter: it captures pointers, reads coalesced samples, draws the stroke in progress once per frame and keeps pages far from the view to their size alone. Every change is one undo step and goes to a background save queue that writes each annotation's latest whole state. Pages are the import's page renders read through the integrity-checked source-asset command, so the webview never parses a PDF; perfect-freehand shapes ink outlines behind `strokeOutline.ts`. Phones get every tool in two rows that fit one screen width: the note tools, the shape tools and zoom fold into menus, undo moves to the second row, and color and size open in a sheet. Text notes stay above the Android keyboard through the IME inset. Automatic zoom fits the page to the window but stops at 125%, where the 120 dpi page renders show at their own resolution. Where the view needs more pixels than those renders have (zoomed in, or a high-density screen), `pageTiles.ts` asks the native `render_document_page_tile` command for 512-pixel tiles of the visible part of each page, redrawn from the stored PDF at a density stepped by √2, once scrolling and zooming have rested; tiles already shown stay underneath until the new ones arrive, and none are stored. While the highlighter is chosen, the canvas reads the text of the pages near the view through the native `get_document_page_text` command (PDFium's characters and their boxes, desktop only) and `textSelection.ts` turns a drag that starts on a character into one box per line plus the words covered, stored as a `highlight` with `rects` and `text` and no `points`; pages without text, and Android, keep free strokes. A sticky note is a `text` annotation marked `sticky`, drawn at a fixed size with its first lines and edited in a Dialog outside the pages so the dialog's pointers never reach the gestures; the native owner allows it longer text than a plain note. The page-image cache belongs to an effect, so a remount (React strict mode in development) gets a fresh cache.

Tutor keeps final PR #94 multi-source selection, safe Markdown, source-optional conversation, private question criteria and hidden-answer/citation safeguards. While a turn runs, the workspace reads its learning-task progress (`get_learning_task_progress`, one read at a time) and shows what it is doing: reading the conversation, finding sources, writing, checking. For an explanation, the native service also passes the public `text` of the streaming structured answer into that progress as `draft`, and the workspace renders it as it grows; citations, saving and history wait for the checked turn, which replaces the draft. Hints, quizzes and grading never set a draft, because their private material must pass its checks first. Questions use Send; do not restore Quiz me. A quiz question renders as `TutorQuizCard` from its public `question` (its place `number` of `total`, its `choices`, and once answered its expected answer, explanation and right option); its graded answer (`questionId`) shows on the card rather than as a turn. Native `tutor/contracts.rs` `QuizSeries` sets a question's place: Next question sends a quiz turn with `afterQuestionId`, and a run with a set length refuses a question past its last. A choose-one answer sends `choice` and is graded in `tutor/service.rs` by `output::grade_choice` with no provider request, depending only on its question's sources; a short answer is graded by the model, which reports `criteriaMet` per saved criterion. Save as flashcard opens `TutorAnswerCards` on the question and expected answer. A finished answer offers Read aloud when a lesson voice is set up (`useVoiceAvailable`): `tutor/useReadAloud` asks `speak_tutor_reply` for one piece at a time and loads the next into a second hidden audio element while the current one plays, so pieces follow without a gap; a second press, another chat or leaving Tutor stops it. Native `tutor/speech.rs` speaks only a complete turn's saved `assistant_text`, read from Markdown as plain sentences with LaTeX math said in words (`tutor/speech/math.rs`) and cut into pieces of at most 400 characters, through the lesson narration's kept `speech_segments` in the speech setting's model and voice. An explanation may show up to two document figures: native `tutor/figures.rs` offers the model only read, worth-studying, unhidden figures on or explained on the retrieved pages, keeps only offered `![title](figure:<document>/<figure>)` images in the saved text, and `get_tutor_figure` hands the reader a figure only for a finished answer that shows it. `TutorFigure` draws it from the PDF page through `render_document_page_tile`, floated beside the text and full width on compact screens; no figure bytes are stored. The latest explanation can be asked again: Regenerate, or Edit on its question, sends a new explain turn with `replacesTurnId`, and native `tutor/turns.rs` admits it only for the conversation's last unreplaced explanation, records the pair in `tutor_turn_replacements` (release schema 24) in the same transaction, and drops the replaced turn's conversation knowledge source. History, summaries and conversation retrieval skip replaced turns; the workspace groups a turn with the finished answers it replaced (`replacedByTurnId`) behind earlier/later arrows, and earlier versions are read only. Attachments: the composer's `useTutorAttachments` stages each picked, pasted or dropped picture in its own `import` asset draft (`stageBrowserImage`, `importImage`) and reads text files as text; `send` passes them as `attachments` on an explain turn. Native `tutor/turns.rs` promotes each picture's asset and writes `tutor_turn_attachments` (release schema 25) in the admitting transaction, and `tutor/context.rs` sends the pictures first (`ImageShows::Attached`, captioned as the learner's) and the files as `attachedFiles`. `tutor/service.rs` refuses pictures before admission when the task's model is not verified for image input (`tutor_images_unsupported`), and the composer reads `get_tutor_image_input` to say so and hold Send. Regenerate, Edit and Try again send a turn's saved attachments again, the pictures as kept assets. Device sync deletes chat pictures with the chat rows. Make flashcards opens `TutorAnswerCards`, which asks `draft_tutor_answer_cards` (the flashcard model, through `ai/document_intelligence/answer_cards.rs`, at most six question/answer drafts from a complete explanation's saved text) and adds the kept, edited cards to a live deck with `bulk_create_cards`; closing the sheet cancels the draft. It is shown only when `useGenerationModelMissing` finds a flashcard model. The composer's microphone (`tutor/useSpeechInput`, recording through `platform/microphone`) appears only where `get_speech_input_status` reports support; the first tap asks before downloading the speech model, a second tap stops, and native recognition puts the text into the draft for the learner to edit and send. A recording that falls quiet after speech for the `speechAutoSendSeconds` setting (default 2, 0 for never; `tutor/speechPause`) stops itself and sends its text as heard. Escape or Discard recording drops it. See [ADR 0061](../decisions/0061-local-speech-input.md). The Documents, guide reader, Progress, active Practice and Tutor layouts use the same scaffold, actions, fields, metrics and feedback while their controllers and rich-content models remain independent. The inactive Practice face is inert, and Tutor submission remains composition-aware. A finished session opens Session complete, which reads `get_session_summary`: the session's counts, the cards it moved into Solid, the missed cards to practice again, what is still due today, and today's totals and streak from the study activity ledger. Until that read returns, or if it fails, the screen shows the counts it kept while answering.

## Overlay lifecycle

Base UI owns browser focus containment/restoration, keyboard interaction, popup positioning, modality and scroll locking through the shared Dialog/Sheet/Menu/Tooltip implementations. OverlayProvider owns application parent/depth registration and native Back dispatch; it is not a duplicate DOM focus trap. Menus, tooltips and toasts float at the overlay shadow level (level 3), above the cards' level 1.

Every Dialog and Sheet, including confirmations and MetadataDialog, shares one structure: a header with the title, optional description and close button; a body that scrolls with standard padding and spacing; and an `actions` footer that stays visible while the body scrolls, with a rule above it while content continues below. `onSubmit` makes the body and actions one form, so a submit action in the footer submits it without navigating. Widths come from four sizes (small, medium, large, workspace). On compact screens a dialog fills the screen, while sheets and confirmations rise from the bottom edge at their content height; both keep safe-area and IME padding.

Only the applicable top layer dismisses. Busy/non-dismissible state, alert-dialog pointer behavior, compact safe-area/IME layout and explicit initial focus remain contracts. Menus unmount before an action opens a dialog. Feature workflows import the shared Dialog/Sheet owners directly; the retired compatibility Modal wrapper is not another lifecycle. Features use semantic confirmation/overflow APIs rather than ordinary `window.confirm` or handwritten backdrops.

An inline workspace stays nonmodal. Its card presentation frames a workspace with a title heading and a close button; its page presentation makes the workspace the page, with a top bar that sticks to the top of the scroll area (back button, title over description, and actions) and leaves the gutters and the page's own h1 to the content, so render it in a PageScaffold without the inset. Browser beforeunload/native active-document shutdown protection remain distinct from an interactive React confirmation, which cannot guarantee completion during every shutdown path.

## Styles, tokens and typography

`src/ui/foundations/index.css` is the single global entry. It defines cascade layers, root sizing, typography, token foundations, platform insets and accessibility capabilities. Tailwind compiles namespaced `tw:` utilities through the Vite plugin without Preflight or a second reset.

All ordinary feature presentation uses Tailwind and shared oStudy components. Utilities occupy the components layer below retained specialized geometry/content overrides; no global important flag is used. Partial separators clear their other border edges explicitly. Do not use global stage sheets or important flags to hide precedence defects.

Reference/semantic/component token sources generate committed artifacts. Themes change values, not feature selectors. Reference tokens hold theme-independent primitives; each theme file owns its palette (including six subject colors with soft variants, which also feed the chart roles), radius scale, shadow levels and primary-button glow, and may alias its own roles (`radius.button` is a pill except in Console). Surfaces are opaque in every theme, without blur or translucency. Text uses the token type scale (caption, label, small, body, body-large, title-small, section, title, display) with bundled line heights; stock Tailwind text sizes are disabled. Headings are semibold with -0.01em tracking in the theme's heading family (the interface font, or IBM Plex Mono in Console); card content keeps its own font. Control height, touch target and icon sizes are rem-based so the interface scale reaches them.

The interface scale sets the root font size, so every rem-based size follows it while media queries (which resolve rem against the initial size) stay put. Layout breakpoints are defined once (`breakpoint.medium` 760px and `breakpoint.wide` 1180px in the reference tokens) and generate both the `viewportQueries` LayoutModeProvider uses and Tailwind's `compact`, `medium` and `wide` variants; CSS Modules reach the variants through `@reference` and a nested `@variant`, so JavaScript and CSS agree at every width. Stacking uses one layer scale, lowest first: behind, base (the application frame, which keeps every in-app layer below portals), selected, focus, raised, sticky, chrome, floating, drag, then the body-level dialog band (nested dialogs add 2 per depth), popover (menus and tooltips), toast and effects. Numeric z-index values are rejected by the UI theme test. The Tailwind adapter maps semantic roles to oStudy variables without overwriting old short aliases or adding a separate dark provider. Utility names are complete source literals, not interpolated fragments.

Stable oStudy facades wrap owned shadcn source in `src/ui/vendor/shadcn`; only that directory imports Base UI. Feature code may use Tailwind but not vendor types/APIs. Current primitives include forms, tabs, Card composition, Item list objects, ButtonGroup/Toolbar actions, badges/chips, progress, notifications, menus and dialogs. Customized copies need reviewed upstream refreshes; they do not update automatically.

Icons come from one set. `Icon` renders Lucide glyphs vendored as path data on Lucide's 24-unit grid with a 1.9 stroke, behind application names such as `cards`, `study-guide` or `stop`; features pass a name instead of drawing their own inline SVG, and a missing glyph is added to `Icon` from Lucide.

### Stock-first visual rule

`components.json` selects shadcn's Base UI Nova family. For ordinary presentation, the default is to use the owned Nova component's sizing, spacing, hierarchy and standard variants rather than recreating the pre-PR #96 appearance. oStudy remains the authority for semantic colors, Light/Dark/Console/Synthwave themes, fonts, accessibility capabilities and product meaning.

A shared application abstraction should exist because it carries product semantics, cross-platform behavior or reusable interaction policy—not merely because it groups Tailwind classes. Prefer Card for bounded information, ListRow for the rows of a list, Item for a standalone list object, Field/FormField for labels/help/errors, Alert/notice for status, and Toolbar/ButtonGroup for related actions. `Surface` remains a compatibility/product-state boundary while generic consumers migrate away from elevation/material vocabulary.

Card is the one card surface: the theme's large radius (20 px, 4 px in Console), a hairline border and the level-1 shadow, drawn flat on phones, inside another card and inside dialogs or popovers. Its `--card-gutter` custom property (20 px, 16 px on phones, 12 px for small cards) pads the slots, and a screen's own padding classes replace it. The compositions over it keep separate jobs: Panel adds a title, description and actions; Surface adds product state (tone, selection, hover for clickable surfaces, an inset well); StatTile adds a label, a value, an optional StatDelta pill whose arrow and hidden word carry the direction, a hint and a small visual, with StatGrid for rows of tiles. Screens apply Card instead of repeating its radius, border or shadow.

Headings come from two components on the type scale. PageHeader holds the page's `h1` at the title size (34 px, 28 px on phones) with an optional eyebrow, a 16 px description and actions that sit beside the title and wrap below it when the row is narrow; a ResponsiveActionGroup passed as the actions collapses secondary ones into an overflow menu on phones. SectionHeading titles a card or a part of a page at 19 px, or at the 24 px section size for a section that groups several cards, with an optional eyebrow, description and actions. Its level follows the outline rather than the size: `h2` under the page title, `h3` inside a dialog or another section. Panel draws its title with SectionHeading, so a titled card and a titled page section read the same.

SegmentedControl chooses one of two to five short options; its option type accepts no fewer and no more, and longer lists belong in a select or a menu. It is a radio group: Tab enters at the chosen option, arrow keys move and choose, Home and End jump to the ends, and the focus ring follows the visible pill. Each option's button is the whole touch target (`max(44px, 2.75rem)`, more on phones) while its pill sits 4 px inside, as in the mockups. Options that cannot share a row move whole to a second row instead of clipping or squeezing their labels. A null value leaves every option unchecked for a choice made beside the control, such as a filter chosen in a sheet beside a row of presets.

ListRow is one row of a list: an optional leading tile, a title, meta lines and trailing status, figures or actions, which wrap below the text when the row is narrow. ListRowMedia draws the mockups' square tile with an icon or a short format label such as PDF. ListRows puts a hairline between rows and, inside a card, runs them to the card's edges while each row indents by the card's gutter. Comfortable rows (16 px titles) suit a few rich items, such as study guides and a subject's documents; dense rows (14 px titles, tighter padding) suit long lists and editing, as on the Workbench mockup, and today carry the Progress page's session and answer lists. With `onActivate`, the tile and text become one button that opens the row, so the row's own actions stay separate buttons beside it instead of nesting inside it. Titles and meta wrap rather than truncate. Item remains the standalone list object.

VirtualList renders only the rows near its viewport, for lists that can run to thousands of rows such as a deck's cards. It owns its scroll area, so it needs a bounded height; rows are measured after they render, so they may wrap, and `onEndReached` asks for the next page as the end comes into view. It keeps list semantics (`aria-setsize` and `aria-posinset` on each row). It is the only place that imports TanStack Virtual, which the UI boundary check enforces. ResizablePanes lays out side-by-side panes for wide screens: fixed panes keep a width in px, one flexible pane fills the rest without shrinking below its minimum, and the handles between them are separators that follow a pointer drag or the arrow keys (Shift for larger steps, Home and End for the limits, double click to restore the default). The caller keeps the widths it reports. Compact screens show one pane at a time instead of using it.

Charts take their colors and type from the theme. SVG and HTML charts can use the chart tokens as CSS variables (`--ostudy-color-chart-1` to `-6` and `--ostudy-color-chart-grid`). Canvas charts cannot read CSS variables, so they take `useChartTheme()` from `src/ui/charts`: the palette, the confidence colors for rating series, text, grid and tooltip colors, and type-scale sizes in the interface font at the current interface scale, read again when the theme, contrast, scale or font changes. `chartAxis`, `chartLegend` and `chartTooltip` give Chart.js muted caption ticks on the chart grid, a legend of line samples in each series' color, width and dash, and tooltips on the overlay surface. `distinctPaletteColors` takes palette colors in order but skips any that sit too close to a color already on the chart, so a series never repeats another's color: Console's first chart color is its success green, which the Easy rating already uses. The Progress page (`src/screens/progress/`) draws its charts in HTML and SVG from the chart tokens, so it needs none of the canvas helpers; each section loads through its own latest-request lane.

Fine-pointer desktop controls follow Nova's compact geometry. Coarse-pointer capabilities expand interactive targets to the application touch minimum without creating a second mobile component tree. Theme differences change semantic values and optional effects, not the information architecture.

Interface/card font and scale preferences remain independent. Current React appearance state consumes `motionPreference`; the native settings reader alone translates historical `animationsEnabled`/`reduceMotion` rows before IPC. Packaged IBM Plex Sans has a system fallback; a fresh source build may provision uncached fonts, but the installed app needs no runtime font service. Explicit user selections remain authoritative; native PDF export has its own print/font contract.

## Responsive and accessible presentation

Wide and medium widths draw the header as a side rail on the left, in its own `navigation` colour (grey on the light theme, a step darker than the content on the dark ones): the raccoon mark, the labeled destinations, then Search and Settings at the bottom; compact keeps the brand, the page title, Search and Settings in a top bar and the five destinations in a bottom bar. Layout follows viewport and capabilities, not OS-name conditionals. Bounded reading measures, intrinsic wrapping and contained table scroll prevent oversized pages or unreadably tiny controls.

Preserve labels, focus, announcements, topmost dismissal, keyboard alternatives, touch targets, enlarged text and safe-area/IME insets. Motion and artwork preferences are distinct. Reduced motion removes nonessential animation without hiding progress. Surfaces are flat and opaque in every theme, so nothing depends on blur or translucency; the stored material preference is kept for settings compatibility but is no longer shown or styled. Educational images and functional status/icons are not decorative artwork.

## Help, tutorials and feedback

HelpProvider uses one registry and shared Sheet presentation; labels/help triggers remain associated without nesting buttons in labels. Tutorials default off and require an explicit user action. Their spotlight target geometry remains custom, while ordinary actions and text use shared UI. Disabling tutorials closes active guidance.

Tutorial progress is versioned device-local state, not a portable study session. Semantic feedback follows completed actions; domain success never depends on animation/haptics or a toast. Base UI renders notifications while the app retains action identity, absolute Undo deadlines and post-commit recovery semantics.

## Testing and cleanup

Test active controllers, route/dirty guards, overlays/Back, library empty/populated/archive states, drag/keyboard movement, authoring identity, imports and sync recovery. CSS compilation discovers the entire production frontend and checks emitted utilities. The AST-based ownership guard rejects raw generic controls outside the vendor layer, with only disabled sanitized Markdown task markers exempt. Native WebDriver/Android tests establish integration not proven by mocks.

Retain dedicated pointer geometry, QR quiet-zone, guided spotlight, inline rich progress, native root-height and document/editor/print CSS with explicit ownership. The ten remaining Modules are registered with rationales in `scripts/ui/presentation-policy.mjs`; the verifier rejects missing, dead or unregistered owners. Do not delete real versioned compatibility readers or unavailable-capability fallbacks merely to reduce source counts.

The committed Stage-0 screenshot matrix is historical provenance, not the current visual specification. During an intentional visual redesign, capture an exact-head **candidate** into ignored `.artifacts/` output, review it separately from behavior gates, and only establish a new committed baseline after human acceptance. Never overwrite the historical matrix to make an intentional difference disappear.
