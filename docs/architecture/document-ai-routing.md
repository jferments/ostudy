# Document AI routing and concurrency

Document hierarchy and provider request boundaries are deliberately separate concerns in ostudy.

Semantic extraction preserves headings, page/source provenance, element types, and section relationships. Provider requests are then packed by bounded source-token and source-unit capacity rather than splitting every time a heading changes. A highly structured textbook must therefore not degenerate into one outline request per heading or page.

For large documents, outline and flashcard windows are independent units of provider work. Cloud-backed windows may execute with bounded concurrency while checkpoint/database writes remain serialized in source-window order. This preserves deterministic durable state while allowing network/inference latency to overlap. Concurrency follows execution topology rather than provider brand: cloud profiles may run up to four independent document windows concurrently, while local and LAN profiles remain serial unless a future explicit server-capacity capability says otherwise.

OpenRouter routing treats compatibility, privacy, and model precision as hard eligibility constraints. Document requests require parameter-compatible endpoints, deny provider data collection by default, honor the profile's optional ZDR requirement, and restrict eligible endpoint quantization to INT8, FP8/MXFP8, FP16, BF16, or FP32 execution. Independent document windows deliberately do not share a sticky `session_id`: they contain different source text, and real-provider acceptance showed negligible prompt-cache reuse while one sticky route could concentrate all concurrent work on the same slow endpoint.

Long document processing is throughput-sensitive rather than price-sensitive. A single job may issue many outline, generation, repair, and curation completions; repeatedly selecting a slow endpoint can therefore multiply a modest per-request delay into tens of minutes. OpenRouter document traffic is explicitly sorted by provider throughput while preserving fallbacks across every otherwise eligible endpoint. The existing p90 preference of at least 50 output tokens/sec and p90 latency preference of at most 20 seconds remain secondary performance signals. This makes endpoint speed the dominant route objective without pinning ostudy to one hosting company or weakening privacy, precision, or structured-output compatibility. Connection probes use the same route policy so a successful profile test exercises the same provider class used by subsequent document work.

Provider resilience is based on transport inactivity rather than a blunt whole-request wall clock. The profile timeout bounds silence while connecting and between received SSE events. Any provider heartbeat/comment, reasoning delta, output delta, tool-argument delta, or final usage event proves the connection is responsive and resets that timer; an active request may therefore run as long as needed. A silent transport failure is retried once with the same logical request. Completed windows remain checkpointed for Retry.

Structured-output exhaustion is deliberately separate from transport failure. The selected model's declared reasoning capabilities are normalized before document planning and the task's requested reasoning effort is resolved once for the job. Optional reasoning is never silently promoted from a requested lower effort to a more expensive unsupported effort; if the requested effort is unavailable and reasoning is not mandatory, document processing disables reasoning for that task. Mandatory-reasoning models use their lowest declared supported effort. The resolved effort is part of checkpoint identity.

Completion budgets reserve visible structured output separately from hidden reasoning. For OpenRouter reasoning models, the wire-level completion ceiling includes reasoning headroom while the document schema retains its provider-neutral visible-output budget. Large-document generation keeps the existing 16-candidate window capacity. If a generation result is genuinely truncated, ostudy may retry that source window with a smaller card count, but the retry never reduces the original completion-token ceiling. A `finish_reason=length` marker alone is not treated as failure: a complete schema-valid structured result is accepted; only an incomplete/invalid result is classified as truncation. Outline truncation receives additional output headroom and must either produce a valid structured fragment or fail explicitly rather than being silently replaced by a low-information native fallback.

Operational token/count telemetry is safe numeric metadata and remains available to diagnostics and the document-usage analyzer, while prompt/completion/source content remains redacted. Provider usage accumulated before a failed document run is persisted with the failure so the document UI cannot change from a real live token count to “not reported” merely because a later window failed.

These rules apply to both initial generation and future document-aware tasks. New document features should reuse semantic chunks, capacity-bounded windows, deterministic native assembly, normalized provider capabilities, and the shared provider routing/concurrency policy rather than introducing feature-specific page loops or unbounded request fan-out.
