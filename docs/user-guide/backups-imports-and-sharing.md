# Backups, imports, and sharing

ostudy uses different formats for different jobs. A personal disaster-recovery backup is not the same thing as a deck shared with a classmate, and neither is the same as a JSON file generated by an LLM. Keeping those boundaries separate prevents accidental transfer of private review history or internal database state.

## Format overview

| Format | Purpose | Includes personal review history? | Includes AI credentials? |
| --- | --- | --- | --- |
| `.studydeck` | Share or transfer one deck | No | No |
| `.ostudy.json` | Import generated card content into one deck | No | No |
| `.ostudybackup` | Restore the complete personal library | Yes | No |

## Share one deck with `.studydeck`

A `.studydeck` file is a versioned SQLite interchange package for one deck. It contains the deck's notes, active card presentations, tags, supported rich content, and managed images needed by those cards.

It deliberately excludes:

- the exporting learner's schedules and review events;
- practice sessions and personal analytics;
- application settings;
- AI provider profiles and credentials;
- reusable authoring templates that are not owned by the deck.

When another learner imports the file, ostudy validates the package and creates fresh local schedules. Their reviews then belong to their own library rather than inheriting the exporter’s due dates or confidence history.

Use `.studydeck` for classroom exchange, sharing with friends, moving a particular deck, or preserving a portable content copy.

## Import generated cards with `.ostudy.json`

A `.ostudy.json` file is strict, UTF-8, data-only authoring input. The file identifies a deck to create or an exactly named active deck to append to, then supplies Basic, Reverse, or Fill in the blank content using the supported restricted Markdown and cloze grammar.

The ordinary **Import deck** action accepts both `.studydeck` and `.ostudy.json`. There is no separate generated-import preview screen. ostudy validates the entire JSON file before opening one transaction. If any card is invalid, the library is unchanged and the error identifies the affected path. Exact duplicates are skipped automatically, and accepted cards receive fresh local schedules.

The file cannot contain internal IDs, SQL, HTML, file paths, images, schedules, reviews, analytics, settings, or deletion/overwrite instructions.

See the [generated JSON reference](../reference/generated-json-import.md), [agent instructions](../reference/flashcard-import-agent.md), [JSON Schema](../ostudy-flashcards-v1.schema.json), and [example file](../examples/cardiovascular.ostudy.json).

## Protect the full library with `.ostudybackup`

A `.ostudybackup` file is the complete personal-library recovery format. It captures one coherent SQLite snapshot and the managed files required by that snapshot, including:

- decks, notes, cards, tags, and templates;
- schedules, review events, practice sessions, and analytics source records;
- ordinary application settings;
- managed card images;
- retained source PDFs and their durable document-processing state;
- nonsecret AI provider metadata, task defaults, and redacted capability evidence;
- completed migration and data-repair ledgers needed for consistent restoration.

Credentials are excluded because credential bytes never enter the SQLite snapshot. Session-only credentials disappear when the process exits; secure credentials remain in the operating-system credential service and must be configured separately on a restored machine.

## When to create backups

Create a complete backup:

- after a substantial authoring session;
- before testing a migration-heavy development branch;
- before replacing a computer or reinstalling the operating system;
- before a risky manual cleanup;
- on a schedule appropriate to the value of the library.

Keep more than one generation and store at least one copy outside the application data directory. A backup located only on the same failing disk is not a complete recovery strategy.

Backup creation is blocked while a document task is active. This ensures the database and managed files are captured at one coherent point rather than packaging an in-progress PDF operation.

## Restoring a backup

A restore is validated before it replaces the active library. The application stages the replacement and applies it through the startup boundary so that a partially copied database or managed directory is never exposed as a normal library.

After restoration:

1. Restart ostudy when instructed.
2. Confirm that decks, images, schedules, recent reviews, settings, and documents are present.
3. Reconfigure or verify AI credentials on the restored machine.
4. Run a small practice session and create a new backup before deleting the older source copy.

Do not rename an arbitrary SQLite database to look like an ostudy backup. The package format and managed-file inventory are validated as a unit.

## Import safety

Treat every imported file as untrusted, even when it came from a friend or a model you control. ostudy validates schema, paths, rich content, links, images, tags, templates, card identities, duplicate behavior, and bounded sizes before persistence. Imports cannot execute JavaScript, SQL, shell commands, or raw HTML.

Validation protects the application boundary, not the factual accuracy of study material. Review shared and generated cards for correctness before relying on them.

## Choosing the right format

Use:

- `.studydeck` when the goal is **share this deck**;
- `.ostudy.json` when the goal is **author these generated cards**;
- `.ostudybackup` when the goal is **recover my complete library**.

Using the narrowest appropriate format makes the result easier to inspect and reduces the amount of personal data transferred.
