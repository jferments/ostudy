# ADR 0040: Canonical multimodal document representation

- **Status:** Accepted
- **Date:** 2026-08-20
- **Scope:** Canonical document foundation following PR #62

## Context

ostudy currently has a capable PDF pipeline: it preserves immutable source bytes, extracts structured PDF content, selectively recovers text with OCR, renders bounded visual evidence, plans semantic windows, builds a reusable outline, and generates curated study material through configured AI providers. The durable and in-memory contracts around that pipeline are still partly page-shaped and PDF-specific, however. PDF backend types cross the ingestion boundary, every source unit is assumed to have one render, and generation/checkpoint records use `page_*` vocabulary even where the underlying concept is a generic source location.

Future adapters must accept presentations, word-processing documents, OpenDocument files, HTML, plaintext, EPUB, and photographed notes without creating parallel semantic, outline, or generation pipelines. Later study guides, practice tests, interactive tutoring, search, and topic mapping must reuse the same document intelligence rather than reinterpret each format independently.

Text extraction is not sufficient for all learning content. A slide diagram, annotated note image, chart, equation, or spatial relationship can carry meaning that is absent from extracted text. Configured multimodal models may interpret selected visual evidence, but provider output cannot replace immutable source provenance or deterministic local extraction.

Small local embedding models may later produce semantic vectors for document chunks and concepts. Embeddings are useful derived indexes for semantic search, topic relationships, and study-needs mapping, but they are model/version dependent and must not become the authoritative document representation.

## Decision

### Three app-owned layers

Every format adapter terminates at an ostudy-owned `CanonicalDocument` containing ordered source units, semantic blocks, assets, provenance, metadata, and extraction diagnostics. Parser-library types do not cross this boundary.

A separate semantic layer derives provider-independent chunks and bounded windows from the canonical document. Source units, semantic chunks, and provider windows remain distinct concepts: units provide durable citation identity, chunks preserve coherent meaning, and windows satisfy model capacity limits.

A standardized document-intelligence layer stores the document summary, outline hierarchy, learning objectives, and key concepts. It is generated from canonical chunks and selected visual evidence and is reusable by flashcard generation and later learning features.

### Source units and blocks

PDF pages, presentation slides, flowing-document sections, EPUB chapters, plaintext segments, and note images are all source units. Paragraphs, headings, list items, tables, equations, captions, speaker notes, and image descriptions are blocks within a unit rather than independent top-level documents.

Source locators carry a source-unit kind, positive ordered unit numbers, an optional section label, optional asset references, and an optional time range reserved for future audio/video adapters. No adapter fabricates geometry for flowing content that has no stable layout.

### Visual evidence is first class

A source unit may own zero, one, or many assets. Assets include page or slide renders, embedded images, diagrams, charts, equations, cover images, and original note photographs. The semantic planner records asset references on relevant chunks, while provider planning selects a bounded, deduplicated evidence set according to verified model capabilities.

Multimodal interpretation is an enrichment over deterministic extraction. Visual descriptions generated by a model are stored with model/provenance identity and confidence limitations; they never overwrite source text, source assets, or adapter output. Text-only profiles continue to work from canonical text when usable text exists.

### Embedding-ready but model-neutral

Canonical blocks and semantic chunks have stable content hashes and source locators. Those identities are the future attachment point for embeddings. A later embedding index may store vectors keyed by chunk ID plus embedding model, revision, dimensionality, normalization, and tokenizer identity.

No embedding model or inference runtime is added by this decision. Embeddings remain rebuildable derivatives and may be deleted or regenerated without changing documents, outlines, cards, schedules, or review history. Candidate runtimes such as Candle and candidate models such as Qwen embedding models require a separate dependency, licensing, mobile-footprint, and quality decision.

### Adapter registry

A `DocumentAdapter` registry performs bounded content probing and selects one adapter from source bytes and package identity; filename extensions and reported MIME types are hints only. Adapters parse local source data, invoke shared OCR when necessary, and return canonical records. They do not select AI profiles, construct prompts, call providers, author cards, or write arbitrary database state.

PDF becomes the reference adapter. Its existing extractor, renderer, OCR recovery, cancellation, and resource controls remain in place but are mapped into canonical source units, blocks, and assets before persistence or semantic planning.

### Persistence and compatibility

The immutable public baseline migration remains unchanged. A new append-only migration introduces generic source-file, source-unit, source-block, and source-asset records and converts existing PDF page data transactionally. Existing document IDs, source hashes, managed files, semantic content, outlines, generation state, and generated decks remain intact.

Generic durable vocabulary replaces page-only vocabulary at domain boundaries. Compatibility reads may be retained only where required during one atomic schema transition; new code does not dual-write two competing representations.

Checkpoint identities include the source-bundle hash, adapter/backend identity, canonical-schema version, semantic-planner version, selected visual evidence, and provider/model/prompt identities. An adapter or OCR upgrade invalidates affected derivatives without changing the immutable source.

## Consequences

- Adding a format adapter is limited to probing, parsing, canonical normalization, and format-specific tests.
- The existing outline, generation, curation, authoring, cancellation, and provider-routing pipeline is reused after canonical normalization.
- PDF behavior must remain the regression oracle while the representation changes.
- Visual material can contribute to all later learning features through bounded multimodal evidence rather than PDF-specific page-image logic.
- Semantic embeddings can be added later without another document-identity redesign.
- Canonical records and assets increase schema breadth, but eliminate format branching from downstream AI and learning workflows.
- Office/EPUB/parser libraries and embedding runtimes remain separate reviewed decisions; this ADR does not add speculative dependencies.
